# M16.2 — Real ∀-quantified user signs in the existing H-Code compiler

**Status:** source implemented on feature branch \`feat/m16-2-universal-sign-types\` (stacked on M16 PR #17). Rust and JS reference suites must pass on the **exact final SHA** before accepting the milestone. No merge to \`main\`.

## Sign-first invariant

\`∀\` means **universal type quantification**, not a for-loop and not a string alias to TypeScript. A type variable is declared explicitly and checked rigidly at the function definition; a new concrete instantiation is inferred independently on each call.

\`\`\`hcode
∀T ƒ head(xs:⟦T⟧)→T ↩ xs⟦0⟧;
∀T ƒ repeat(xs:⟦T⟧)→⟦T⟧ ↩ xs⧺xs;
\`\`\`

The accessibility fallback is \`forall T fn head(xs:[[T]]) -> T return xs[[0]];\`. This compiles to equivalent semantics, although its **source spans differ** because it is longer.

These definitions are actual pure H-Code source; \`⊚\`, \`⊛\`, \`⥇\`, \`⥈\` and other package-owned glyphs are not built-in TypeScript or AI macros.

## Actual reusable library (format 3)

\`packages/poly.signs/lib.hc\` contains the two definitions above, SHA-256 protected by \`hcode.m16.2.lock.json\`. \`packages/poly.signs/manifest.json\` exports arbitrary non-core Unicode glyphs \`⥇\` and \`⥈\` with explicit \`"typeParameters": ["T"]\`.

\`\`\`hcode
use "poly.signs@1.0.0" as poly;
print(poly∷⥇(⟦2,3,5⟧));
print(poly∷⥇(⟦"a","b"⟧));
print(poly∷⥇(⟦⊤,⊥⟧));
print(⌗poly∷⥈(⟦2,3⟧));
print(⌗poly∷⥈(⟦"a","b"⟧));
\`\`\`

Expected stdout: \`2\`, \`a\`, \`true\`, \`4\`, \`4\` on separate lines. Every call genuinely specializes the same function for a distinct type. Nested lists are checked recursively; mixed elements, unbound/empty \`T\` inference, wrong arity, illegal \`Any\` and forbidden primitive operations on rigid \`T\` are errors.

## Source-of-truth compiler and security contract

- **Rust lexer/AST/parser:** \`∀\` and \`forall\` are the same token; binders are explicit, scope-limited, unique and capped at eight; v1/v2 H-Code syntax is preserved. No input program may declare an unverified generic H-Code function outside a pure locked library.
- **Rust checker:** \`Type::Generic(name)\` is rigid during function-body proof. It is **not** \`Type::Variable(id)\` and cannot unify with concrete \`Number\` or \`String\`. Each \`alias∷glyph\` expression creates a fresh map of type inference variables for every bound type parameter, so successive calls can safely use \`Number\` and \`String\`. Source may contain locally typed \`≔x:T\` declarations inside a generic function.
- **Rust package loader:** format 3 checks actual source binders, parameter names/types, returns and pure source bodies with the existing H-Code checker. SHA-256, local-file, Unicode-normalization, glyph collision, effects and size rules remain in force from M16. Formats 1 and 2 still run unchanged.
- **JS reference:** existing H-Code parser plus \`package-v2-types.mjs\` validates each H-Code declaration and body with rigid type strings; \`package-v3-signatures.mjs\` infers and substitutes concrete input/result types **per invocation**, including nested sequences and runtime bounds. Generic source functions are instantiated internally and their local annotations are verified. Package or source is rejected if unsigned or different from the SHA lock. Bare universal functions in a regular application are rejected, like the Rust compiler.
- **Runtime:** source compiles to ordinary verified H-Code functions; no \`eval\`, host/network API, arbitrary JavaScript plugin or AI inference is used. Node-generated execution is **not a general sandbox** for hostile native JS.
- **No unchecked Any:** unbound generic variables, unconstrained \`⟦⟧\`, heterogeneous sequence elements, accidental coercion and false polymorphic implementations are all rejected.

## Scope limits (do not overclaim)

Format 3 currently handles rank-1, explicitly bound type parameters in concrete/scalar/sequence signatures. It does not yet implement quantified **function-typed manifest parameters**, higher-kinded types, arbitrary effect polymorphism, recursive public typeclasses or unconstrained generic application functions. Pure package source and its exported functions are checked. Full Studio package discovery from verified metadata is still a separate follow-up.

Historical M10/M13/M14/M15 benchmark files are untouched. The existing **three-task** and **eight-task** measurements cannot prove the canonical 20-task 70% hypothesis; no new overall percentage is claimed. The package manifest and lockfile are currently separately authored JSON files and must be counted in a full dependency-aware authoring comparison. **M16.3 should generate redundant metadata/lockfiles from concise sign-first definitions** to avoid erasing code-point gains through JSON boilerplate; generated bytes and dependencies remain reported separately.
