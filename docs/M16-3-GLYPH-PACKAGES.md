# M16.3 — glyph-first package authoring (in progress)

Author one pure, typed function per glyph in `packages/<name>/signs.hcs`. **The glyph replaces the function keyword and the identifier**; the author never writes `ƒ head` or `ƒ repeat`. Generic binder syntax stays real compiler semantics:

```hcode
∀T ⥇(xs:⟦T⟧)→T ↩ xs⟦0⟧;
∀T ⥈(xs:⟦T⟧)→⟦T⟧ ↩ xs⧺xs;
```

The generator constructs private `ƒ g1` and `ƒ g2` function identifiers **only in generated code**. This is checked by M16.2's existing Rust compiler and JS package loader: the symbols execute actual typed H-Code bodies, not macros or string-only aliases.

Generate and validate offline with the real Rust typechecker and the existing format-3 package loader:

```bash
cargo run --manifest-path compiler/Cargo.toml -- pack --name poly.auto --version 1.0.0 --source packages/poly.auto/signs.hcs --lock hcode.m16.3.lock.json
cargo run --manifest-path compiler/Cargo.toml -- pack --name poly.auto --version 1.0.0 --source packages/poly.auto/signs.hcs --lock hcode.m16.3.lock.json --check
cargo run --manifest-path compiler/Cargo.toml -- run packages/poly.auto/demo.hc --lock hcode.m16.3.lock.json
node prototype/bin/hcode.mjs run packages/poly.auto/demo.hc --lock hcode.m16.3.lock.json
```

`lib.hc`, `manifest.json`, and `hcode.m16.3.lock.json` are generated and SHA-locked. Existing `poly.signs` artifacts and the old M16.2 lock remain untouched. The authoring file is forced to LF in `.gitattributes` for cross-platform SHA identity. Before output writes, a temporary candidate package is typechecked, signature-checked and hash-verified with the existing format-3 Rust package loader; invalid package definitions leave existing output files alone. Both compilers load the existing format-3 representation. `--check` fails if any generated file differs; the loader also verifies the hashes and typed source. No generated bytes count as developer-authored text; imported code and handwritten `.hcs` source do.

### Two separate benchmarks — do not conflate them

**Historical M14** is preserved byte-for-byte and executed by `npm run m14:measure`. On the exact same three SHA-frozen programs, M14's *median* is **68.46% fewer Unicode codepoints** than the TypeScript sources; individual tasks: sum **83%**, map **68.46%**, filter **67.07%**. That result has not been erased or replaced by the package test.

**M16.3** is a different workload: two generic reusable functions, one package and four application calls, with authored package source **and import/demo included**. The TypeScript benchmark input is unchanged. Prior glyph authoring is preserved as `compact/benchmarks/m16-3/pre-glyph-name-legacy.hcs`, with its own frozen SHA-256. New authoring removes `ƒ head` and `ƒ repeat`.

| Input | Developer-written Unicode codepoints | UTF-8 bytes |
|---|---:|---:|
| Prior M16.3 H-Code package + demo | 175 | 249 |
| **Direct-glyph M16.3 package + same demo** | **159** | **231** |
| Same TypeScript source | 230 | 230 |

Thus M16.3 savings improve from **23.91%** to **30.87%** on this *one microcase*; the old M14 result remains **68.46%** on its own three-program corpus. This comparison does not establish 70% across the canonical 20 programs. Unicode source can still occupy more UTF-8 bytes than ASCII-heavy TypeScript. The actual generated `lib.hc`, JSON manifest and lock bytes are reported separately by `node scripts/m16-3-authoring-metrics.mjs` and are never hidden.

Benchmark protections: both M16.3 authoring revisions and TypeScript remain SHA-256-frozen; TypeScript parity and generated Rust/JS execution are tested; the original M14 SHA/outputs are checked separately in CI. **Never quote 23.91% or 30.87% as an updated overall H-Code compression score.**

### Safety and scope

- Source must be a normal `.hcs` file under `packages/<name>/`, with one eligible user glyph directly defining each function (no extra `ƒ` or function name); reserved, duplicate, unbound, effectful or normalization-unstable names are rejected.
- `--check` is side-effect-free and fails if any generated file has drifted.
- New candidate source/manifest/lock are checked by the signed package loader **before modifying outputs**; existing v1/v2/v3 locks stay compatible.
- Limitations: rank-1 generics and concrete/sequence types inherited from M16.2; no higher-kinded types. The compiler is not an execution sandbox. There is not yet an atomic **three-file transaction** against disk write failures.
- Windows and Linux Rust/JavaScript/metrics CI on the exact final PR SHA is the release gate. Do not merge stacked branches without reviewing the ancestor PRs.
